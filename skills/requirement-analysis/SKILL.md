# 需求分析与测试点提取

把需求文档转化为一组**可核对、无遗漏、无歧义**的测试点,是用例质量的源头。
用例的覆盖度问题,90% 是测试点提取阶段的遗漏。

分析分两个层次:**显性需求**(文档写了什么)与**隐性质量**(文档写得对不对、全不全)。
只提取显性需求是初级水平;能发现文档本身的缺陷才是需求分析的价值。

## 工作流程

### 1. 通读文档,建立上下文
- 先完整 read_file 需求文档(文档长时分段读完,不要只读开头就动手)。
- 记录三样东西,作为后续分析的锚点:
  - **角色清单(Actor)**:文档涉及哪些角色(普通用户/管理员/客服/系统定时任务…),
    每个角色能做什么;
  - **术语表**:业务专有名词及其定义(如"冻结""核销""有效订单"),术语理解错,
    后面全错;
  - **业务主流程**:用一句话串起核心业务闭环(如:下单→支付→发货→确认收货→结算)。

### 2. 需求质量预检(专业动作,不可跳过)
逐段扫描文档,识别需求本身的缺陷。歧义词清单与常见需求缺陷模式见
references/ambiguity-checklist.md,重点拦截:
- **不可测试词**:"尽量、合理、快速、大量、友好、等、必要时"——凡出现必追问量化标准;
- **缺失的验收标准**:有功能描述但没有"做到什么程度算完成";
- **缺失的异常路径**:只写成功流程,没写失败/超时/并发时的行为;
- **单位与精度缺失**:金额精度、时间时区、数量上限未定义。
发现的每一处都记入「需求疑问」清单,**禁止静默假设后跳过**。

### 3. 划分功能模块,提取功能点与业务规则
- 按业务功能划分模块(如:登录、注册、订单、支付),模块名沿用文档中的术语。
- 功能点 = 文档明确描述的一条系统行为。提取时遵守:
  - **忠于原文**:文档没写的功能不臆造;每个功能点能回指到文档出处(章节/段落);
  - **原子化**:一个功能点只描述一个行为;"用户可以搜索并按价格排序"拆成两个功能点。
- **业务规则单独提取**:凡是文档中的"必须/只能/不超过/当…时/若…则"类约束,
  单独提取为规则(BR 编号),并写清触发条件与系统动作。
- **数据约束单独提取**:字段级约束(类型、长度、必填、唯一、默认值、取值枚举)
  整理成数据约束表,这是边界值用例的直接输入。

### 4. 识别非功能需求
文档显式声明或行业惯例隐含的非功能需求,逐类检查并提取为测试点:
- **性能**:响应时间、并发量、大数据量下的表现(有量化指标按指标,没有记入疑问);
- **安全**:认证、授权、敏感数据保护、注入防护(参照测试点清单的安全维度);
- **可靠性**:重试、幂等、事务补偿、降级与熔断;
- **兼容性**:文档声明的浏览器/系统/机型范围;
- **易用性**:文案规范、错误提示的可理解性。

### 5. 把功能点扩展为测试点
每个功能点从以下维度展开成测试点(完整清单见 references/test-point-checklist.md,
提取完必须逐节对照自查):
- **正常维度**:基本流、典型输入、常见业务路径;
- **边界维度**:数值/长度/时间/数量/分页的边界点;
- **异常维度**:非法输入、空值、重复提交、超时、网络中断、并发操作;
- **权限维度**:未登录、无权限、横向/纵向越权、角色差异;
- **数据维度**:初始数据、数据联动、数据一致性、幂等性;
- **非功能维度**(如适用):性能、安全、兼容、可靠性;
- **体验维度**(如适用):文案与提示语、交互细节。

### 6. 挖掘隐式需求与矛盾
- **隐式需求**:文档没写但行业惯例要求具备的(如密码不明文显示、删除需二次确认、
  金额服务端二次校验),提取为测试点并标注「隐式」;
- **矛盾与缺失**:文档前后矛盾、与常识冲突、关键规则缺失(如"密码错误几次锁定"
  没写次数)时,记入「需求疑问」清单。

### 7. 输出测试点文档
用 write_file 把结果写入 `/analysis/<doc_name>-test-points.md`,格式:

```markdown
# <文档名> 测试点分析

## 分析上下文
- 角色:普通用户、管理员
- 业务主流程:注册 → 登录 → 下单 → 支付 → 收货
- 术语:有效订单 = 已支付且未取消的订单

## 模块一:登录
### 功能点
- F-LOGIN-01:用户可使用手机号+密码登录(出处:2.1 节)
### 业务规则
- BR-LOGIN-01:密码连续错误 5 次,账号锁定 30 分钟(出处:2.3 节)
### 数据约束
| 字段 | 类型 | 约束 |
|---|---|---|
| 手机号 | 字符串 | 必填,11 位数字,唯一 |
| 密码 | 字符串 | 必填,6-20 位,须含字母和数字 |
### 测试点
- TP-LOGIN-001 [正常]:正确手机号+密码登录成功,跳转首页
- TP-LOGIN-002 [边界]:密码长度下限(6 位)登录
- TP-LOGIN-003 [异常]:密码错误登录,提示"手机号或密码错误"
- TP-LOGIN-004 [权限]:未登录访问首页,跳转登录页
- TP-LOGIN-005 [安全]:密码输入框不明文显示,接口返回不携带密码
- TP-LOGIN-006 [隐式]:登录失败提示不区分"账号不存在"与"密码错误"(防账号枚举)

## 需求疑问
- Q1:文档未说明密码连续错误是否锁定账号,按"暂不锁定"设计用例,待确认
- Q2:2.1 节"登录要快速响应"不可测试,建议量化为"P95 响应 < 2s",待确认

## 假设记录
- A1:假设短信验证码有效期 5 分钟(文档未写),相关测试点按此设计
```

规则:
- 测试点编号:`TP-<模块缩写>-<三位序号>`,后续用例编号与之对应,保证可追溯;
- 功能点/业务规则编号:`F-<模块缩写>-<两位序号>` / `BR-<模块缩写>-<两位序号>`;
- 每个测试点标注维度标签([正常]/[边界]/[异常]/[权限]/[数据]/[安全]/[性能]/[隐式]);
- 输出后在回复中向用户汇报:模块数、功能点数、业务规则数、测试点数、需求疑问清单。

## 质量红线
- 文档中每一条"必须/只能/当…时"约束,都至少有一个对应测试点;漏一条就是漏一类缺陷;
- 每一个不可测试词都必须进入「需求疑问」,禁止默默自行解释;
- 不确定的地方列入「需求疑问」并写入「假设记录」,禁止静默假设;
- 测试点之间不重复、不互相包含;
- 权限、安全、异常三个维度任何模块都不得为空——为空说明分析不到位,返工。
