# 需求粗扫(广度优先)

详细分析(requirement-analysis)是"深度优先":通读 → 模块 → F-points → 7 维度 TP,
代价高、单文档要消耗大量 token;粗扫只做第一步和第三步的前半段,目的是**让用户
能在付出详细分析成本之前,从候选模块里挑出要测的范围**。

广度优先 ≠ 粗制滥造;粗扫结果要保证列出的每个模块在文档里都有据可查,
不臆造、不遗漏主流程涉及的功能模块。

## 工作流程

### 1. 通读文档,识别结构
- 用 read_file 通读需求文档(分段读完,先看目录/章节标题,再扫章节首段);
- 关注四类结构线索:
  1. 显式的「模块/子系统/功能/菜单」标题;
  2. 一级或二级标题的并列关系(同一层级的并列项 = 候选模块);
  3. 角色清单里的角色权限边界(每个角色能做的事 = 一个或多个模块);
  4. 业务流程图里的节点(每个节点 = 一个候选模块)。

### 2. 候选模块划分
- 按业务功能划分模块,模块名沿用文档中的术语(必要时附中文释义);
- 粒度标准:
  - **上限**:粗扫模块数 5-15 个;超过说明分得太细,合并相邻模块;
  - **下限**:不可少于 3 个(只列 1-2 个说明没在粗扫);
- **忠于原文**:文档没写的功能不臆造;每个模块能回指到文档出处(章节号/段落);
- 主流程涉及的模块必须全部出现,即使文档写得简略。

### 3. 输出候选模块清单
用 write_file 把结果写入 `/analysis/<doc_name>-rough-scan.md`,格式:

```markdown
# <文档名> 粗扫结果

## 候选功能模块清单
按文档顺序列出,每条格式严格:

### <模块名>
- **模块 ID**:M-<两位序号>(如 M-01、M-02)
- **文档出处**:第 X 节 / <段落标题>
- **用途一句话**:这一模块是做什么的(15-30 字,从文档原文提炼,不臆测)
- **复杂度预判**:低 / 中 / 高(按涉及状态机、外部依赖、数据约束综合判断)

### <下一个模块>
...

## 主流程路径
用一条路径把候选模块串起来,反映文档里的核心业务闭环:
M-01 → M-03 → M-05 → M-07 ...

## 粗扫统计
- 模块总数:N
- 高复杂度模块数:N(列出 ID)
- 文档章节跨度:第 X 章 ~ 第 Y 章
```

## 质量红线
- 每个模块都要有**文档出处**;没出处的模块剔除,不进入清单;
- **主流程路径**必须存在(若文档没说主流程,自行标注"文档未明说主流程");
- 严禁在粗扫阶段写 F-points / BR / TP,那属于详细分析;
- 模块数低于 3 或超过 15,回到 step 2 重新调整粒度。

## 与详细分析(requirement-analysis)的关系
粗扫产出 `/analysis/<doc_name>-rough-scan.md`,**只供用户挑选 scope**;
详细分析(requirement-analyzer)读取的是同一份需求文档,按用户选定的模块
重新执行 step 3-7。粗扫结果不直接喂给详细分析。
