# 测试用例设计

把测试点转化为**可执行、可判定、可追溯**的测试用例。
核心原则:对不同的测试点选用匹配的设计技术,而不是所有场景都套同一种方法。

## 技术选择矩阵

| 测试点特征 | 首选技术 | 说明 |
|---|---|---|
| 单个输入字段的取值校验 | 等价类 + 边界值 | 有效/无效等价类各取代表值,边界取 min-1/min/min+1/max-1/max/max+1 |
| 多个条件组合决定一个结果 | 判定表 | 条件数 ≤5 时全组合;条件多时用正交/Pairwise 裁剪 |
| 条件之间有依赖/约束关系 | 因果图 | 先画因果图再转判定表,避免漏掉组合约束 |
| 功能有明显的状态流转 | 状态迁移 | 画出状态图,覆盖所有合法迁移 + 关键非法迁移 |
| 端到端业务流程 | 场景法 | 基本流 1 条 + 每个备选流至少 1 条 + 高风险备选流组合 |
| 配置/兼容性组合爆炸 | 正交试验 / Pairwise | 用正交表或成对组合把组合数压到可执行量级 |
| 接口契约与参数 | 接口用例设计 | 参数校验矩阵 + 状态码 + 契约字段,见 techniques.md 第 8 节 |
| 性能/安全等非功能点 | 非功能用例设计 | 指标量化 + 场景化,见 techniques.md 第 9 节 |
| 需求模糊或经验性风险 | 错误推测 | 基于历史缺陷经验补充,放在最后兜底 |

详细技术与示例见 references/techniques.md(各技术操作步骤)、
references/examples.md(登录模块 + 订单模块完整设计示例,以及示例三的
**常见打回案例反例对照**——动笔前先扫一遍,避免犯已被打回过的错误)和
references/test-data.md(测试数据设计)。拿不准用哪种技术时,先读这三个文件。

## 设计步骤

1. **读取测试点文档** `/analysis/<doc_name>-test-points.md`(若不存在,先委派
   requirement-analyzer 完成测试点提取);同时回读「需求疑问」与「假设记录」,
   相关用例按假设设计并在用例名称或步骤中体现假设。
2. **逐测试点选技术**:按上表为每组测试点选定设计技术。组合型测试点必须先列出
   判定表/状态图等中间产物(写入用例文件的「设计过程」附录),再展开用例,
   不要直接凭感觉枚举。
3. **展开为用例**:一个测试点可展开为多条用例(如边界值 6 个点 = 6 条用例),
   但一条用例只验证一个测试点,保持原子性。
4. **补齐要素**(逐字段规范):
   - **用例名称**:`<动作> + <条件/数据> + <预期>` 的一句话概括,
     如"密码错误 5 次后账号锁定 30 分钟",让人不看步骤就知道这条测什么;
   - **前置条件**:分层写明——环境(浏览器/版本)、账号(角色/权限)、
     数据(已存在的业务数据,写到具体值);
   - **测试步骤**:"操作 + 数据"粒度(点哪个按钮、在哪个页面、输入什么),
     多步用「;」分隔;数据必须具体化(见 test-data.md);
   - **预期结果**:可观察的判定标准(页面文案、跳转地址、状态变化、数据落库),
     与步骤一一对应,禁止"正常""正确"这类词。
5. **测试数据设计**:按 references/test-data.md 为每条用例配具体数据,
   禁止"一个合法手机号"这类抽象描述。
6. **按风险标定优先级**(不要拍脑袋,按矩阵评):

   | 影响 \ 概率 | 高(主路径/高频操作) | 中(常见分支) | 低(罕见场景) |
   |---|---|---|---|
   | **致命**(资损/数据丢失/安全泄露/主流程阻断) | P0 | P0 | P1 |
   | **严重**(核心功能失效但有绕行方案) | P1 | P1 | P2 |
   | **一般**(边缘功能失效、体验受损) | P2 | P2 | P3 |
   | **轻微**(文案、样式、极端边缘) | P3 | P3 | P3 |

## 用例编号与追溯
- 编号格式:`TC-<模块缩写>-<三位序号>`,与测试点编号 `TP-<模块缩写>-<三位序号>`
  同模块对应,保证每个测试点都能找到覆盖它的用例;
- 设计完成后自查:把测试点清单逐条过一遍,确认每条都有用例覆盖;
  未覆盖的要么补用例,要么在交付说明里写明原因;
- 「设计过程」附录中的**追溯矩阵是覆盖率核对的权威来源**:评审与 lint 工具
  以矩阵为准做双向核对。矩阵必须与实际用例表一致——改了用例表必须同步改矩阵,
  脱节本身就是严重问题。

## 输出契约(与下游流程强绑定)
- 用例表必须是六列 Markdown 表格,列顺序固定:
  `用例编号 | 用例名称 | 前置条件 | 测试步骤 | 预期结果 | 优先级`
- 单元格内禁止出现 `|` 和换行(步骤多步用「;」分隔,数据示例用中文逗号);
- 表头必须与此完全一致,差一个字导出工具都会拒绝;
- 完整用例表用 write_file 写入 `/testcases/<doc_name>-testcases.md`(覆盖写,
  始终保持全量最新版本);**导出 Excel 由主 agent 执行,本子代理不调用导出工具**;
- 「设计过程」附录固定包含三部分,附在用例文件末尾:
  1. **设计中间产物**:判定表、状态图、因果图等;
  2. **追溯矩阵**:四列表格,表头固定
     `测试点编号 | 测试点摘要 | 覆盖用例编号 | 设计技术`;
     测试点文档中**每个测试点一行**,覆盖用例编号列出展开出的全部 TC
     (至少一个,多个用「、」分隔);
  3. **分布统计**:按模块、按优先级的用例数量(各一小段列表即可),
     交稿前自查分布是否失衡(如某模块明显偏少、P0 占比过高)。

## 质量红线
- 同一用例表里不出现重复或互相包含的用例;
- 每条用例的执行步骤和预期结果一一对应;
- 测试数据具体化:写"手机号 13800001111"而不是"一个合法手机号";
- 异常场景用例占比 ≥ 30%,纯正向用例集一律打回重做;
- 权限与安全类测试点必须有对应用例,不得因"文档没细写"而跳过;
- 涉及资金、库存、计数类的用例,必须包含并发/重复提交的验证。
- 产出后主 agent 会用 lint_testcases 工具做机械检查(表结构、编号连续性、
  模糊词、抽象数据、异常占比),命中即打回;交稿前按以上红线自查可减少往返。
