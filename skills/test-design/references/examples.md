# 完整设计示例

## 示例一:登录模块(等价类 + 边界值 + 判定表 + 状态迁移)

需求摘录(假设):用户可用手机号+密码登录;手机号 11 位数字;密码 6-20 位,
须含字母和数字;连续错误 5 次锁定 30 分钟;登录成功跳转首页。

### 第一步:技术选择

- 手机号/密码格式校验 → 等价类 + 边界值
- 「账号存在 × 密码正确 × 是否锁定」组合 → 判定表
- 「未登录 → 已登录 → 锁定」状态流转 → 状态迁移

### 第二步:判定表(组合条件)

| 条件 | R1 | R2 | R3 | R4 | R5 |
|---|---|---|---|---|---|
| 账号存在 | T | T | T | F | F |
| 密码正确 | T | F | — | T | F |
| 账号已锁定 | F | F | T | — | — |
| 动作:登录成功 | ✓ | | | | |
| 动作:提示密码错误 | | ✓ | | | |
| 动作:提示已锁定 | | | ✓ | | |
| 动作:提示账号或密码错误 | | | | ✓ | ✓ |

(R4/R5 提示语一致:防账号枚举,属于安全隐式需求。)

## 示例二:订单模块(状态迁移 + 场景法 + 幂等)

需求摘录(假设):订单状态流转为 待支付→已支付→已发货→已完成,
待支付 30 分钟未支付自动取消,已支付未发货可申请退款(退款后订单关闭);
库存不足时下单失败;支付接口异步回调。

### 第一步:技术选择

- 订单生命周期 → 状态迁移
- 下单→支付→收货主链路 → 场景法
- 支付回调乱序/重复 → 错误推测(时序类)

### 第二步:状态迁移图(写入「设计过程」附录)

```
待支付 --支付成功回调--> 已支付 --发货--> 已发货 --确认收货--> 已完成
待支付 --超时30分钟/用户取消--> 已取消(终态)
已支付 --申请退款且未发货--> 退款中 --退款成功--> 已关闭(终态)
```

非法迁移需验证拒绝:已取消订单再收到支付回调、已发货订单申请仅退款、
已完成订单再取消。

### 第三步:展开用例(节选)

| 用例编号 | 用例名称 | 前置条件 | 测试步骤 | 预期结果 | 优先级 |
|---|---|---|---|---|---|
| TC-ORDER-001 | 下单支付收货主流程 | 商品 SKU1001 库存 10,用户已登录并有收货地址 | 下单商品 SKU1001 数量 1;用测试支付账号完成支付;商家后台发货并填单号 SF123456;用户确认收货 | 订单状态依次变为 待支付→已支付→已发货→已完成;库存由 10 变为 9;每一步状态变化后列表页与详情页一致 | P0 |
| TC-ORDER-002 | 超时未支付自动取消 | 订单创建于 29 分 50 秒前 | 等待 15 秒;刷新订单详情页 | 订单状态变为已取消;库存回补;不可再支付(支付按钮置灰) | P1 |
| TC-ORDER-003 | 取消后支付回调乱序到达 | 订单已因超时取消,但用户此前已在支付页发起支付 | 模拟支付成功异步回调到达 | 订单保持已取消状态,不变更为已支付;回调记录进异常日志;若已扣款触发自动退款流程 | P0 |
| TC-ORDER-004 | 支付回调重复到达 | 订单已支付 | 同一笔支付成功回调重复推送 2 次 | 订单状态保持已支付不变;不重复扣减库存;不重复发送通知 | P0 |
| TC-ORDER-005 | 重复提交下单请求 | 商品 SKU1001 库存 1,用户已登录 | 在下单页快速双击「提交订单」按钮 | 只生成 1 个订单;库存扣减为 0;不出现重复订单 | P0 |
| TC-ORDER-006 | 库存不足下单失败 | 商品 SKU1001 库存 0 | 下单商品 SKU1001 数量 1 | 下单失败,提示「库存不足」;不生成订单;优惠券未被锁定 | P1 |
| TC-ORDER-007 | 已发货订单申请仅退款被拒 | 订单状态为已发货 | 用户在订单详情点击「申请退款」选择仅退款 | 提示「已发货订单不支持仅退款,请申请退货退款」;退款单不生成 | P1 |
| TC-ORDER-008 | 并发下单不超卖 | 商品 SKU1001 库存 1,两个账号同时下单 | 账号 A、B 同时提交该商品订单各 1 件 | 只有一个订单成功;另一个提示「库存不足」;库存不为负数 | P0 |

## 示例三:常见打回案例(反例对照)

以下是从评审打回记录中提炼的高频问题。设计时逐条自查,可以避免绝大多数返工。
每条给出 ❌ 被打回的写法、打回原因和 ✅ 修正后的写法。

### 反例 1:预期结果模糊(最高频)

❌ `预期结果:登录正常`
打回原因:「正常」没有判定标准,执行人无法判定通过/失败。
✅ `登录成功,跳转首页,右上角显示脱敏手机号 138****1111`
要点:预期必须可观察——页面文案、跳转地址、状态变化、落库字段,至少写一项。

### 反例 2:测试数据抽象

❌ `测试步骤:输入一个合法手机号和正确的密码`
打回原因:执行人不知道具体输什么,不同人执行结果可能不同;
且「一个值测全部」容易掩盖缺陷。
✅ `输入手机号 13800001111 和密码 Abc123`
要点:写到可直接输入的值;同一字段的不同用例用不同的值。

### 反例 3:一条用例验证多个测试点(缺陷屏蔽)

❌ `输入空手机号和 5 位过短密码,点击登录,预期:提示输入有误`
打回原因:两个无效等价类混在一条用例里,前一个校验报错会掩盖后一个
——即使密码长度校验根本没做,这条用例也能"通过"。
✅ 拆成两条:TC-A 手机号留空、密码合法 Abc123,预期「请输入手机号」;
TC-B 手机号合法 13800001111、密码 5 位 Abc12,预期「密码长度为 6-20 位」。
要点:无效等价类一类一条用例;一条用例只验证一个测试点。

### 反例 4:前置条件不可达

❌ `前置条件:账号已锁定`
打回原因:执行人不知道怎么让账号进入锁定状态,用例无法执行。
✅ `前置条件:已注册手机号 13800001111,已连续输错密码 5 次触发锁定,
锁定时间未满 30 分钟`
要点:特殊状态要写明到达路径(怎么造这个数据)。

### 反例 5:用例名称不达意

❌ `用例名称:测试登录功能 3`
打回原因:不看步骤根本不知道这条测什么,评审和回归时无法快速定位。
✅ `用例名称:密码错误 5 次后账号锁定 30 分钟`
要点:名称 = 动作 + 条件/数据 + 预期,一句话概括。

### 反例 6:步骤与预期不对应

❌ 步骤有 3 步(打开页面、输入数据、点击提交),预期只写最后一步的结果
打回原因:中间步骤没有断言,页面没打开、数据没输入成功都会被漏掉,
失败时也无法定位是哪一步的问题。
✅ 预期与步骤一一对应:`页面打开,显示登录表单;手机号与密码回显输入值;
点击后跳转首页,右上角显示 138****1111`

### 反例 7:资金/库存类缺少幂等与并发

❌ 下单功能只设计了:正常下单、库存不足、取消订单
打回原因:资金/库存/计数类功能的标配是幂等 + 并发,缺了就是资损风险,
评审一律打回。
✅ 必补:重复提交(双击/重发请求只生成一单)、并发不超卖(两人同时买
最后一件,只有一人成功且库存不为负)、回调重复/乱序到达(状态不重复变更)。

### 反例 8:定级过松或一刀切

❌ 全部用例定 P1;或「按钮文案错别字」定 P0
打回原因:定级失去意义,回归时无法按优先级裁剪。
✅ 按定级矩阵逐条评:资损/数据丢失/安全泄露/主流程阻断才是 P0;
纯文案、极端边缘场景不高于 P3。健康分布:P0 占 10%-20%。

### 反例 9:纯正向用例集

❌ 20 条用例全是合法输入、正常流程
打回原因:异常场景占比红线 ≥ 30%;缺陷恰恰集中在异常路径。
✅ 每个功能点至少补:无效等价类逐类一条、边界外一点、关键非法状态迁移、
权限缺失/越权、并发或重复提交(涉资金库存时)。

### 反例 10:用例间互相包含

❌ TC-A「正确账号密码登录成功」与 TC-B「正确账号密码登录后显示用户名」
打回原因:B 完全包含 A 的验证点,两条重复,执行两遍浪费工时。
✅ 合并为一条,预期同时覆盖跳转与用户名展示;或让 B 聚焦差异点
(如用户名超长时的截断展示),与 A 错开。
