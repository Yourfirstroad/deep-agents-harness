# 测试用例评审

用例初稿完成后、导出交付前,必须过一遍评审。
评审目标:**覆盖度无遗漏、用例可执行、无冗余、优先级合理、格式合规。**

职责边界:评审者**只审不改**——发现问题写入评审报告并给出可执行的修订意见,
修订动作由用例设计者完成;修订后需对修订点重新评审,形成闭环。

## 评审流程

### 1. 覆盖度核对(最重要,双向追溯)
- 打开 `/analysis/<doc_name>-test-points.md`,以用例文件「设计过程」附录中的
  **追溯矩阵为基准**逐条核对;矩阵缺失、或与实际用例表脱节,本身就是严重问题;
- **正向核对**:每个测试点在矩阵中有对应行,且所列覆盖用例真实存在;
  未覆盖的逐条列出 TP 编号 + 原因,不允许只写"基本覆盖";
- **反向核对**:矩阵引用的每条用例都在用例表中存在;用例表中有但矩阵
  未引用的用例,检查是否臆测需求(标注「疑似臆测」,交需求疑问确认);
- **抽查矩阵真实性**:随机抽 5-10 行,确认所列用例确实验证了对应测试点
  (防止矩阵与用例"两张皮");

### 2. 逐条质量检查
按 references/review-checklist.md 的清单逐条过,重点拦截:
- 预期结果模糊(出现"正常""正确""成功"而无具体判定标准);
- 步骤不可执行(缺测试数据、缺操作对象、依赖未说明的前置状态);
- 用例重复或互相包含;
- 一条用例验证多个独立测试点(应拆分);
- 用例名称不达意(无法从名称看出"什么条件下做什么、预期什么")。

### 3. 优先级合理性
- 对照定级矩阵:资损/数据丢失/安全泄露/主流程阻断必须是 P0;
- P0 用例占比通常在 10%-20%;超过 30% 说明定级过松,逐条复核;
- 纯 UI 文案、极端边缘场景不应高于 P3;
- 警惕"全是 P1"的偷懒定级。

### 4. 量化指标统计(报告必须包含)
| 指标 | 计算方式 | 合格线 |
|---|---|---|
| 测试点覆盖率 | 已覆盖 TP 数 / TP 总数 | 100%,不足逐条说明原因 |
| 异常场景占比 | 异常/权限/安全类用例数 / 总用例数 | ≥ 30% |
| 步骤-预期对应率 | 步骤与预期一一对应的用例数 / 总用例数 | 100% |
| 数据具体化率 | 测试数据全部具体化的用例数 / 总用例数 | 100% |
| P0 占比 | P0 用例数 / 总用例数 | 10%-20% |

### 5. 格式合规(导出前硬性检查)
- 六列顺序:用例编号 | 用例名称 | 前置条件 | 测试步骤 | 预期结果 | 优先级;
- 单元格内无 `|`、无换行;
- 编号格式 TC-<模块>-<三位序号>,无重复、无跳号;
- 优先级只出现 P0/P1/P2/P3。

### 6. 输出评审报告
用 write_file 写入 `/review/<doc_name>-review.md`:

```markdown
# <文档名> 用例评审报告

## 结论
通过 / 需修订(修订后需对修订点复审)

## 量化指标
| 指标 | 数值 | 是否达标 |
|---|---|---|
| 测试点覆盖率 | 95% (38/40) | 否 |
| 异常场景占比 | 35% | 是 |
| ... | ... | ... |

## 覆盖度
- 未覆盖清单:(逐条列 TP 编号 + 原因,无则写"无")
- 疑似臆测用例:(无来源的用例编号,无则写"无")

## 问题清单
问题分级:**阻断**(覆盖缺口、主流程缺失、资损/安全风险未覆盖)>
**严重**(不可执行、预期错误、判定标准缺失)>
**一般**(数据不具体、名称不达意、定级不当)>
**建议**(可优化的写法)。

| 序号 | 级别 | 用例编号 | 问题类型 | 问题描述 | 修订意见 |
|---|---|---|---|---|---|
| 1 | 阻断 | —(缺用例) | 覆盖缺口 | TP-PAY-007 并发支付无对应用例 | 补充并发下单场景用例,验证不超卖 |
| 2 | 严重 | TC-LOGIN-003 | 预期模糊 | 预期写"登录正常"无判定标准 | 改为"跳转首页,右上角显示 138****1111" |

## 统计
- 用例总数:P0 x 条 / P1 x 条 / P2 x 条 / P3 x 条
- 问题分布:阻断 x / 严重 x / 一般 x / 建议 x
```

### 7. 修订闭环
- 存在**阻断**或**严重**级问题时,结论必须为「需修订」,并在回复中把
  问题清单原文给出(主 agent 会据此委派设计者修订);
- 修订意见必须可逐条执行:写明改哪条用例、改成什么样,禁止"建议优化一下";
- 只有 0 阻断、0 严重时才允许结论「通过」;仅剩一般/建议级问题时,
  结论可为「通过」但需列出遗留清单。

## 质量红线
- 覆盖率 < 100% 时必须显式说明每个未覆盖测试点的原因,禁止静默放过;
- 评审报告不能只写"已检查,无问题"——必须列出量化指标与核对过程;
- 评审者只输出意见,不直接修改用例文件;
- 修订意见必须落到具体用例编号和具体改法,空泛意见视为评审未完成。
